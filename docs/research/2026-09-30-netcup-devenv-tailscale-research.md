# Netcup NixOS: devenv Machines, Tailscale, and host policy

> Research note, current to 2026-09-30. Primary-source research. Repository-specific statements describe the checked-in configuration and supplied context; recommendations are distinguished from measured facts. The earlier [Machines minimal-layer note](devenv-machines-minimal-layer.md) remains useful background and is not repeated wholesale.

## Executive recommendation

Keep NixOS as the durable host contract: boot/disk, SSH, firewall, Tailscale daemon and enrollment, system services, service users/isolation, and update/recovery policy. Keep development and app-stack iteration in the repository's `devenv shell`/`devenv up` layer. `machines install` is an installer workflow driven by the CLI on the machine running it; it does not install the `devenv` CLI as a NixOS package. The workstation continues to use the pinned `bin/devenv` wrapper. A Home Manager role installs the matching CLI for `hbohlen` on Netcup when the workstation first applies a saved post-install plan.

For access, keep the existing public SSH path until Machines operations have been deliberately moved to a tailnet-connected caller and a console/rescue recovery path is proven. Then use a default-deny host firewall and provider firewall with public TCP 80/443 only for intentionally public web endpoints, SSH only from trusted source ranges or tailnet as operationally appropriate, and optional inbound UDP 41641 to improve direct Tailscale paths. The host firewall and Netcup firewall are separate layers. Do not disable NIC offloads or change MTU without a before/after reproduction; inspect first. Treat the 2026 Linux 7 TSO/GSO report as a relevant upstream report, not evidence that this Netcup VM has the same issue.

## `devenv machines install`: mechanics and what remains

The official [Machines guide](https://devenv.sh/machines/) describes `install` as connecting to a Linux host over root SSH, booting a temporary NixOS installer via kexec, detecting hardware, building the configured system, partitioning with disko, installing NixOS, and rebooting. The target need not already run NixOS. Required installation-time conditions documented by devenv are root SSH, kexec support, `tar`, `curl`, and about 1 GB free RAM for the temporary installer; it needs a suitable disk layout/boot configuration, and the client needs matching build architecture or a configured builder. The standard install phases are `kexec`, `facter`, `disko`, `install`, `reboot`. Build occurs before disko changes disks; disko is destructive by default, without confirmation, dry-run, or automatic resume. Inspect disk identity and target before install/retry. [Machines install documentation](https://devenv.sh/machines/).

The installed host receives the configured NixOS system closure and persistent system configuration: the normal NixOS module defines services, users, bootloader, networking, hardware, etc. The installer can additionally write one-time bootstrap payloads: `install.encryptionKeys` before disko; `install.extraFiles` after `nixos-install`; `install.secrets` after extra files; and optionally copy installer SSH host keys before reboot. Those bootstrap mappings are install-only; subsequent `machines deploy` does not refresh them. [Machines install and bootstrap docs](https://devenv.sh/machines/).

**Important distinction:** `machines install` does not install devenv itself as a NixOS package. The command is executed by the caller's devenv CLI; installation builds/installs the NixOS role's system closure. A `devenv` executable appears on the target only if another declared mechanism provisions it. The guide's `environment.systemPackages` examples are ordinary NixOS package declarations, not implicit installer behavior. On this repo, Home Manager installs the 2.4.0 CLI for `hbohlen` when the workstation first applies a saved post-install plan. The package comes from the root flake for the already-locked devenv input, while `bin/devenv` remains the workstation's wrapper and bootstrap. `self-deploy.nix` supplies the Nix features and supporting system packages, not the CLI package. (Repository: [`hosts/netcup/cli.nix`](../../hosts/netcup/cli.nix), [`bin/devenv`](../../bin/devenv), [`self-deploy.nix`](../../hosts/netcup/self-deploy.nix).)

For a reviewed update, `machines plan` builds and records every role output, including the Home Manager activation, without copying or activating it. `machines apply <plan-id>` sends and activates those exact saved outputs after checking that the declared machine still matches the plan. `machines deploy` combines planning and applying in one command. Prefer plan/apply for this change so you can inspect both the NixOS system and the Home Manager CLI package first. [Machines plan and apply docs](https://devenv.sh/machines/); [devenv 2.4.0 plan implementation](https://github.com/cachix/devenv/blob/v2.4.0/devenv/src/devenv/machines.rs).

NixOS deployment has watchdog rollback/health-check support; the default health check only checks system paths, not application readiness. The Home Manager role activates after the system role and has no automatic rollback. This repo keeps that role to the `devenv` CLI package. Keep bootstrap enrollment material valid across reinstall and keep a recovery route before tightening access. [Home Manager rollback semantics](devenv-machines-minimal-layer.md#1-the-role-model).

### Repo-specific role split

|---|---|---|

## Tailscale on this NixOS VPS

### Daemon, datapath, control plane

NixOS's Tailscale service module enables `tailscaled`; the host config needs the TUN device/kernel support and root-capable daemon for ordinary Linux kernel networking. The default Linux Tailscale interface is a TUN device (`tailscale0`, normally MTU 1280); “userspace networking” is a separate `--tun=userspace-networking` mode, principally for unprivileged daemon use and not the normal NixOS VPS choice. Tailscale documents kernel forwarding as the preferred mode for heavily used Linux routers; this host is a regular endpoint, not a subnet router or exit node, so do not enable forwarding/router features without a use case. [NixOS Tailscale module](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/networking/tailscale.nix); [kernel vs. netstack](https://tailscale.com/docs/reference/kernel-vs-userspace-routers).

The control plane/coordination service authenticates and coordinates peers, distributes device public keys, policies, routes and DNS settings; user data does not transit the coordination service. The data plane is device-to-device encrypted WireGuard, using direct UDP when NAT traversal succeeds and DERP over TCP/TLS 443 as relay fallback. Existing connections can continue with cached state during a control-plane outage, but new peer setup/policy changes/key changes are impaired. [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes); [firewall ports](https://tailscale.com/docs/reference/faq/firewall-ports).

No public inbound Tailscale port is required for basic connectivity: outbound TCP 443 to coordination/DERP plus outbound UDP/STUN/WireGuard traffic is sufficient for clients to operate, with DERP fallback if direct reachability fails. Opening the daemon's UDP listen port (41641 by default; verify actual setting) inbound is optional but often beneficial for unsolicited peer-to-peer reachability and performance. Restricting outbound access to a hard-coded DERP IP list is fragile because the relay fleet changes. The Tailscale port guidance recommends outbound TCP 443, UDP from source 41641, UDP to 3478 for STUN, and optionally TCP 80 for coordination/captive portal behavior; these are egress requirements, not a demand to expose inbound ports. [Tailscale firewall ports](https://tailscale.com/docs/reference/faq/firewall-ports).

### Auth, expiry, and unattended access

Repository configuration enables `services.tailscale`, reads `/var/lib/tailscale/authkey`, pins node name `nc`, and does not set `openFirewall`; the key is installed by Machines only at install time. Existing host's secret was populated separately. (Repo: [`tailnet.nix`](../../hosts/netcup/tailnet.nix); [`devenv.nix`](../../devenv.nix).) Tailscale auth keys bootstrap node registration; their own expiry (1–90 days, default 90) is distinct from the enrolled node key. Revoking an auth key does not deauthorize a node already using it. Default device/node-key expiry is 180 days, and expiry can be disabled per device; tagged devices have key expiry disabled by default. For an unattended server, a pre-approved tagged auth key and explicit tag ownership/least-privilege policy are appropriate, with node key expiry disabled only if the owner accepts the lost reauthentication checkpoint. Rotate/revoke bootstrap keys, and understand that changing `install.secrets` does not rotate the already-installed file. [Auth keys](https://tailscale.com/docs/features/access-control/auth-keys); [key expiry](https://tailscale.com/docs/features/access-control/key-expiry); [tag best practices](https://tailscale.com/docs/features/tags#best-practices).

Unattended startup is compatible with a systemd daemon and auth-key file; it does not remove node-key expiration policy. Monitor expiry and maintain a console/rescue recovery route. If only Tailscale SSH will be allowed, expiry can lock the operator out; the admin console can temporarily extend an expired key for 30 minutes, but that recovery assumes console access and an operator can reauthenticate. [Key expiry recovery](https://tailscale.com/docs/features/access-control/key-expiry).

### Tailscale SSH vs regular SSH

Tailscale SSH is an optional, separately enabled feature (`tailscale set --ssh`) that intercepts SSH to the node's Tailscale IP on port 22 and uses tailnet policy/authentication. It does not rewrite normal `sshd_config` or `authorized_keys`; normal SSH remains independently available. It requires both network access rules and an SSH-specific `ssh` policy, and supports accept/check (reauthentication) modes. [Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh).

For this repo, do not assume Tailscale SSH replaces the key-based OpenSSH path used by `devenv machines install/deploy`: Machines documents root SSH and target's explicit authorized key. Keep normal sshd with public-key-only auth; allow root key auth (`PermitRootLogin = prohibit-password`) while the Machines workflow depends on `root@...`. This is a significant residual privilege; limit who holds that operator key, avoid adding passwords, and maintain sudo operator access. If migrating SSH to tailnet-only, prove the caller itself is on the tailnet, test `machines check`/deploy from that caller, preserve localhost self-deploy, and retain Netcup console/rescue access before removing public SSH. `machines check` cannot see provider firewall policy or prove possession of a usable key. [Machines SSH/deploy checks](https://devenv.sh/machines/).

### Tailnet-only services and routing

Use tailnet ACL/grants to limit which identities can reach the tagged server, and bind private-only applications to loopback or the Tailscale address/interface; a host firewall can additionally scope inbound services to `tailscale0`. For deliberately public web frontends, expose only the reverse proxy's intended ports and keep admin dashboards/upstreams private. Do not assume Tailscale membership alone authorizes every user; policy is the authorization layer. This server has no stated subnet-router or exit-node role: do not enable IP forwarding or advertise routes/default routes, which add routing exposure and are irrelevant to endpoint management. [Access control](https://tailscale.com/docs/features/access-control); [subnet routers](https://tailscale.com/docs/features/subnet-routers); [exit nodes](https://tailscale.com/docs/features/exit-nodes).

## Performance: GRO/GSO/TSO, MTU, and Netcup

### What evidence supports

Linux offloads are not synonyms: TSO segments large TCP transmit buffers in NIC/driver path; GSO is generic software segmentation; GRO coalesces received packets. UDP segmentation offload (`tx-udp-segmentation`) is a different facility. The kernel documentation explains these interfaces and tunnel handling; offloads normally reduce per-packet processing rather than constituting an inherent fault. [Linux kernel segmentation-offload documentation](https://docs.kernel.org/networking/segmentation-offloads.html).

There is a Tailscale GitHub report opened 2026-05-16 for asymmetric throughput degradation on Linux 7.0 in Proxmox/Ubuntu and multiple physical NIC types, with author-provided `iperf3` measurements and a reported workaround disabling `tx-udp-segmentation` and `generic-segmentation-offload` on the physical NIC. This is an issue report and reproducible evidence for that submitter's systems, not a Tailscale-confirmed general defect or a Netcup-specific finding; affected platform was Proxmox 9.1.11/K7, and the report states not everyone is affected. It does not establish that GRO, GSO, and TSO all need disabling, or that Netcup's virtual NIC has the same path. [Tailscale issue #19777](https://github.com/tailscale/tailscale/issues/19777).

The measured state of this exact Netcup VM is not in the research inputs: no live `ethtool`, `ip link`, kernel/driver, route/path MTU, packet capture, `tailscale status` direct-vs-relay result, or controlled throughput baseline was provided. Therefore no claim is made that this host has an offload or MTU problem. The issue is a hypothesis to test only if actual asymmetric loss/throughput symptoms occur.

### Safe diagnostic order

1. Record `uname -r`; `ip -br link`; `ip -d link show tailscale0`; `ip route get <peer>`; `tailscale status` and `tailscale netcheck`. Use `ethtool -i <uplink>` and `ethtool -k <uplink>` to identify virtual NIC driver and current feature state. Netcup virtualization presents a guest-visible virtual device, so inspect inside the guest rather than infer the physical host NIC; no first-party Netcup document found here describes guest NIC offload toggles or guarantees the provider's physical offload configuration.
2. Distinguish transport path: `tailscale ping <peer>` reports direct or relay; `tailscale ping --tsmp <peer>` tests through WireGuard without host networking; ordinary `ping` exercises host networking. Run repeatable `iperf3` both directions on the same direct peer pair and record retransmits, CPU and elapsed time. Tailscale explicitly recommends these layered pings when diagnosing TCP connectivity. [Tailscale TCP troubleshooting](https://tailscale.com/docs/reference/troubleshooting/network-configuration/tcp-connection-two-devices).
3. Inspect link MTU (`ip link`) and candidate route/path MTU with `tracepath`/DF probes where supported; capture ICMP too-big/fragmentation-needed and tunnel traffic with `tcpdump`. Tailscale sets `tailscale0` MTU to 1280; a smaller underlay path/interface MTU or blocked PMTU signals can make larger traffic fail silently. Do not assume setting WAN MTU to 1280 is the right first fix. Tailscale suggests lowering LAN MTU or TCP MSS clamping where packet-size evidence supports it. [Tailscale MTU troubleshooting](https://tailscale.com/docs/reference/troubleshooting/network-configuration/tcp-connection-two-devices).
4. Establish an unchanged baseline, then test one reversible feature at a time on the guest's actual uplink with `ethtool -K <uplink> tso off`, `gso off`, `gro off`, or `tx-udp-segmentation off` only if supported, measuring each and restoring the recorded previous setting immediately afterward. A single changed option with repeated bidirectional measurements is diagnostic; blanket disabling is not justified. If the toggle improves behavior, preserve before/after output and kernel/driver evidence, test persistence only in a separate reviewed change, and report upstream/provider-specific evidence.
5. Consider MSS clamping only when packet-size/PMTU evidence supports it and identify the actual forwarding boundary; MSS clamping affects TCP, not arbitrary UDP. Tailscale's 1280 interface MTU is the overlay MTU, while outer WireGuard UDP/IP headers and provider path MTU are separate constraints. Avoid increasing Tailscale MTU blindly. [Tailscale troubleshooting](https://tailscale.com/docs/reference/troubleshooting/network-configuration/tcp-connection-two-devices); [site-to-site MTU/MSS guidance](https://tailscale.com/docs/features/site-to-site).

Netcup's first-party firewall docs cover filtering but do not establish a universal VPS guest MTU, NIC driver, GRO/GSO/TSO behavior, or performance limit. The current config says disk hardware is VirtIO for `/dev/vda`, but that is not proof of the network adapter model. Obtain guest measurements and the exact product/virtualization data before attributing symptoms to Netcup. Netcup's documented firewall is an upstream policy distinct from NixOS's netfilter firewall; for new servers it allows traffic initially except mail, while existing-server state depends on applied policy. [Netcup firewall documentation](https://www.netcup.com/en/helpcenter/documentation/server/firewall).

## Firewall and host-hardening policy

### Two firewall layers, different semantics

NixOS `networking.firewall` controls the guest host's packet filtering; `services.tailscale.openFirewall` can open Tailscale's configured UDP port in that host firewall and defaults to false in the NixOS module. Current repo comments report the evaluated NixOS baseline as default-deny with SSH TCP 22 allowed by the OpenSSH module; that is a repository measurement for its pinned nixpkgs, not a reason to leave policy implicit. Declare an explicit host policy for intended services and verify evaluated ports after changes. [NixOS Tailscale module source](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/networking/tailscale.nix); [NixOS firewall option reference](https://search.nixos.org/options?query=networking.firewall).

Netcup's SCP firewall is provider-side and independent. Its docs say it is stateful for TCP return traffic, but UDP requires ingress and egress rules; adding ingress/egress policies can change implicit defaults to DROP, so preserve DHCP/NTP/DNS and outbound HTTPS as relevant. Provider firewall rules apply at the public interface and are not a replacement for the local firewall. Netcup recommends ingress-only rules where possible. [Netcup firewall](https://www.netcup.com/en/helpcenter/documentation/server/firewall).

### Minimal inbound policy

Start from the actual intended exposure:

* TCP 80/443 from anywhere only if public HTTP/HTTPS service is intended. This repo's current ingress module is in progress; confirm what binds to these ports before opening them. Keep internal admin/gateway ports unexposed publicly; bind to loopback/Tailscale interface and authorize through tailnet policy.
* TCP 22: currently needed as public root SSH for Machines install/deploy. Restrict at provider and host layer to a stable trusted source IP/CIDR if operationally feasible, but only after confirming the operator's egress IP and recovery path. If caller runs on tailnet, allow SSH through Tailscale while removing public exposure only after deploy and recovery are tested. Maintain loopback access for the host's self-deploy path. Machines `check` does not validate external firewall rules.
* UDP 41641 inbound is optional: omit initially for least exposure and accept that some peer pairs may use DERP; add if measurements show relay use or performance need and the provider path allows it. If added, allow only the Tailscale daemon's actual configured port. `openFirewall = true` concerns the host firewall only, not the Netcup SCP firewall. Do not open UDP 3478 inbound merely because STUN uses 3478: Tailscale's guidance describes outbound UDP to DERP/STUN endpoints. Preserve outbound TCP 443 and ordinary DNS/NTP/DHCP as needed; avoid restrictive egress policy until all service and boot dependencies are enumerated. [Tailscale ports](https://tailscale.com/docs/reference/faq/firewall-ports); [Netcup firewall](https://www.netcup.com/en/helpcenter/documentation/server/firewall).

### SSH, privilege, updates, secrets, services

Retain `PasswordAuthentication = false` and `KbdInteractiveAuthentication = false`; use authorized keys. `PermitRootLogin = prohibit-password` is not equivalent to disabling root login: it permits root public-key access. Here it is an explicit Machines requirement (`root@152.53.92.126`) and therefore a deliberate tradeoff, not a generic hardening default. Keep the operator user separate, use sudo, protect the root-authorized deployment key, and do not widen Nix `trusted-users` without a separate trust review. Nix trusted users have powerful build/substitution privileges; repository currently leaves default root-only trust. [Machines root SSH requirement](https://devenv.sh/machines/); [Nix daemon settings reference](https://nix.dev/manual/nix/2.28/command-ref/conf-file.html).

Nix store paths are readable by design: never put secret contents in Nix strings or path literals. The repository correctly maps SecretSpec value into a root-owned `0600` runtime path instead. Treat `/var/lib/tailscale/authkey` as a bootstrap credential; rotate it deliberately, account for install-only semantics, and avoid logs/command arguments that expose the value. Limit system services to dedicated users and filesystem/network permissions where practical; only bind services publicly when intended. Follow NixOS's declarative update/rebuild process, review deployment plan/health check, and schedule reboot when kernel updates require it; do not mistake system-path health check for application health. [Machines secrets and deploy docs](https://devenv.sh/machines/); [NixOS manual](https://nixos.org/manual/nixos/stable/).

Keep journald/systemd logs available for sshd, tailscaled, firewall and app units; maintain correct time sync because auth, TLS, logs and key lifecycle depend on time. Back up irreplaceable application data and keep provider console/rescue access available: NixOS generation rollback does not reverse application data writes, and Machines docs explicitly identify limits of rollback/recovery. (This is operational guidance, not a claim that the current host has a particular data service.)

## Operational caveats and evidence gaps

* `machines install` is destructive and install bootstrap values are not deploy-time reconciliation. Reinstall key delivery and target host-key verification need deliberate handling. [Machines docs](https://devenv.sh/machines/).
* Tailscale node key expiration can break remote administration. A tagged server normally has expiry disabled by default, but verify the actual admin-console state; do not infer it from Nix config. [Auth keys](https://tailscale.com/docs/features/access-control/auth-keys).
* The state of the live Netcup firewall policy, host NIC/offloads/MTU, provider's virtualization implementation, whether Tailscale peers use direct paths or DERP, current service listeners, and live tailnet ACL/tag/key settings were not inspectable from repository source. Validate these from the Netcup SCP, host and tailnet admin console before applying a firewall cutover or performance workaround.
* `machines install/deploy` is experimental in devenv 2.4 according to the official guide; pinning `bin/devenv` is useful, but recheck upstream behavior before relying on internals.
